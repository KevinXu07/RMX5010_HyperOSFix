# 迅雷 / 中国银行闪退根因线索（2026-11-10）

## 现象

- 迅雷、中国银行（`com.chinamworld.bocmbci`）启动约 1 秒即退出，反复出现。
- `dumpsys activity exit-info` 显示 `reason=2 (SIGNALED)`、`status=9 (SIGKILL)`，即被信号杀死，不是 Java 崩溃。
- 用户反馈：第一版随刷机包打包的模块（1.5.7 一代）正常，后续版本开始闪退。

## 根因（2026-11-10 23:15 实机确认，取代下文“Zygisk 注入层”推断）

**触发点是模块自己 `camera_fix.sh` 对 `/system/lib64/libnativewindow.so` 的 bind mount，与 Zygisk 在应用命名空间里卸载该 bind 的组合。** LSPosed/Zygisk 注入本身不是检测目标。

1. **谁发的 SIGKILL**：ftrace `signal_generate`（`sig == 9`）显示 SIGKILL 由迅雷进程自己的一个线程发出，先杀主进程组再杀自己，不是 system_server/lmkd。中国银行同样。
2. **检测逻辑**：kprobe（`do_sys_openat2` / `vfs_fstatat`，带 `ustring` 路径）追踪该线程：打开 `/proc/self/fd`、`/proc/self/maps`，然后按 maps 顺序对每个文件映射 `stat()`（首个是 `app_process64`，随后是 `libDexHelper.so`，即梆梆加固），在 `stat("/system/lib64/libnativewindow.so")` 之后 0.6 ms 发 SIGKILL。即 **maps 里的 inode 与磁盘 `stat()` 的 inode 不一致 → 判定库被替换**。只差 st_dev（overlay 的 `2f` vs 原分区 `fe:16`）、inode 相同的库不会触发。
3. **为什么不一致**：
   - `camera_fix.sh:363` 把 `$MODDIR/camera/libnativewindow.so`（P010 补丁版，位于 `/data`，dev `fe:49` inode 193969）bind 到 `/system/lib64/libnativewindow.so`（init 命名空间）。zygote 预加载该库，所有应用继承映射 `fe:49/193969`。
   - 对处于“卸载模块”的应用（Zygisk Next `just_umount`，按 SukiSU 的 umount 名单），应用命名空间里来源在 `/data/adb` 的 bind 被卸掉；`/system/lib64` 的 overlay（upper 在 `/data/local/tmp/rmx_camera`）不受影响仍在。于是应用内 `stat()` 得到原厂文件 `2f/30348945`，与 maps 的 `fe:49/193969` 不一致。
   - 实测：init / zygote / system_server / 桌面 / 天气 / Scene 的命名空间中 bind 存在（maps 与 stat 一致）；systemui / phone / xmsf / 安全中心 / 迅雷中 bind 被卸掉（不一致）。
4. **A/B 验证**：
   - `umount -l` 掉该 bind + 重启 zygote（zygote 改为映射原厂 `fe:16/30348945`）：迅雷两次冷启动 10–12 s 后主进程仍存活；中国银行同样存活（仅一个辅助子进程自行退出，主进程不受影响）。
   - 恢复 bind + 重启 zygote：迅雷再次约 1 s 被自杀，maps `fe:49/193969`，应用命名空间 stat `2f/30348945`。
5. **与此前实验/版本差异的对应**：
   - 1.5.7：bind 早已存在，但设备没有 Zygisk Next，应用命名空间不卸载 bind，maps 与 stat 一致 → 正常。
   - 1.7.0 起自动部署 Zygisk Next，“卸载模块”生效，bind 被从应用命名空间卸掉 → 不一致 → 被杀。
   - `disable-zygisk true` 存活：没有 Zygisk 执行卸载，bind 保留，一致。
   - SukiSU UMOUNT / `enforce_denylist=1` 仍被杀：两者都会卸掉 bind，只会让不一致更确定。
   - 早先“只 `znmod disable zygisk_lsposed` 即存活”这次未复现验证，按上述机制不应影响结果，可能是当时实验条件不同，暂不作为依据。
   - 已排除：LSPosed system_server 桥接探测（迅雷全部 binder 事务中没有 `_LSP` = `0x5F4C5350`，杀进程线程本身无 binder 调用）。

### 修复（已实现，待真机重启复验）

- `camera_fix.sh`：`camera_overlay_system_libs()` 把 `$CAM_DIR/libnativewindow.so` 复制进 `sys_upper`；`ensure_camera_port()` 先用 `cmp` 确认 `/system/lib64/libnativewindow.so` 已是补丁版，只有 overlay 没生效时才 bind。
- 2026-11-10 23:19 实机验证（设备有 PIN，未做整机重启；在线复现新的挂载布局：`umount -l` 原 bind 与原 `/system/lib64` overlay，按新逻辑重建 overlay（upper 含模块 `system/lib64` + 补丁 `libnativewindow.so`），再重启 zygote）：
  - zygote maps `00:29/186`（tmpfs upper），应用命名空间 `stat` `ff/186`，inode 一致；应用命名空间里 `/system/lib64` overlay 仍在。
  - 迅雷两次、中国银行一次冷启动 12 s：主进程存活，无指向主进程的 SIGKILL；迅雷停在隐私协议弹窗，可正常交互。
  - OplusCamera：映射的是补丁版 `libnativewindow.so`（`00:29/186`），后置拍照（2.4 MB JPEG）、录像（1.3 MB MP4）、切前置拍照（7.8 MB JPEG）均成功，crash 缓冲区为空、无新 tombstone。
  - Sense：system_server hooks 在 zygote 重启后重新安装（23:19:31）。
- 尚需：整机重启后确认 post-fs-data 日志出现 `camera: libnativewindow-p010 via system lib overlay`，并重复上述冷启动 / 相机检查。

### 当初的修复思路

- **推荐**：不要用来自 `/data/adb` 的 bind 替换 zygote 会加载的库。把补丁版 `libnativewindow.so` 放进 `camera_overlay_system_libs()` 已有的 `/system/lib64` overlay upper（tmpfs `sys_upper`），删除第 363 行的 bind。overlay 在应用命名空间里不被卸载，overlay 下文件的 inode 与 maps 一致（与其余 `/system/lib64` 库同样只差 st_dev，梆梆不判）。overlay 失败时再回退到 bind。
- 回归：迅雷、中国银行冷启动；OplusCamera P010 路径（预览/拍照/录像不崩）；对开启 UMOUNT 的应用复测（若某工具连 `/system/lib64` overlay 也卸载，问题会以同样形式复现）。
- 同类隐患：在 bind 被卸掉的 systemui 命名空间里，除 dmabuf/ashmem 伪文件外，inode 不一致的真实文件只有 `libnativewindow.so` 和 `/product/overlay/DevicesAndroidOverlay.apk`（`post-fs-data.sh:37` 的 `overlay_mount`，同样从 `/data/adb/modules/rmx5010_fod_bridge/overlay/` bind）。A/B 中只去掉 `libnativewindow.so` 两个应用即存活，说明该 apk 目前不触发（可能没被这些应用映射，或检测只看 `.so`），但属于同一类风险，建议一并改成不被卸载的方式。

## 早期实机对照实验（RMX5010，模块 1.7.5 / versionCode 42；结论已被上文“根因”取代）

| 条件 | 结果 |
|---|---|
| 现状（ZygiskNext + LSPosed + hma + keymint 全部启用） | 迅雷约 1s 被 SIGKILL |
| `zygiskd disable-zygisk true` + 重启 zygote | 迅雷正常启动并保持存活 |
| Zygisk 开启，`znmod disable zygisk_lsposed`（LSPosed 的 zygisk 模块）后重启 | 迅雷正常启动，到达隐私弹窗 |
| Zygisk 开启、LSPosed 启用 | 复现 SIGKILL |

结论：触发点在 **Zygisk 注入层**——LSPosed 的 zygisk 库会被注入每个应用进程（即使该应用不在 LSPosed scope 内，`.so` 仍会加载），加固/风控类应用检测到后由自身的守护子进程读 `/proc/<pid>/maps`、`/proc/<pid>/status`，再对主进程和自己发 SIGKILL。ZygiskNext 本体（不加载 lsposed 模块时）不足以触发。后续 UMOUNT 实测（见下文）进一步表明：即使 LSPosed 的 `.so` 已经不在应用 maps 里，只要 Zygisk 注入层还在，迅雷仍会被杀。

## 为什么 scope 里没有这些应用也会被检测

LSPosed 是两层结构：

1. **Zygisk 注入层**：`zygisk_lsposed` 本身是一个 Zygisk 模块，Zygisk Next 会把 `zygisk/arm64-v8a.so` 和 `libzn_loader.so` 映射进**每一个从 zygote fork 出来的应用进程**，与该应用是否在 LSPosed scope 里无关。scope 不是“按应用挂载”，而是决定 LSPosed 拿到进程后**是否加载 Xposed 模块（Sense）并应用 hooks**。
2. **scope / hooks 层**：只有 scope 内的应用才会加载 `com.zephiel.sense` 并执行 hooks。

实机证据（2026-11-10，重启后）：

- 全设备有 17 个进程的 `/proc/<pid>/maps` 包含 `/data/adb/modules/zygisk_lsposed/zygisk/arm64-v8a.so`。
- 其中包括完全不在任何 scope 里的应用：`com.miui.home`（桌面）、`com.miui.weather2`、`com.android.quicksearchbox`、`com.miui.gallery`、`com.xiaomi.xmsf`、`com.omarea.vtools` 等。
- 也就是说，应用自检读 `/proc/self/maps` 时能直接看到 `zygisk_lsposed` 这个模块路径字符串（以及 `zygisksu` 的 `libzn_loader.so`），检测到的是 **LSPosed 的注入基础设施**，不是 Sense 的 hook。

因此“SukiSU 没有给这些应用挂载模块”也不影响：要让某个应用不被 Zygisk 注入，必须在 SukiSU 里给该应用打开 **UMOUNT**（即 Zygisk Next 的 denylist / per-app unount），LSPosed 的 scope 与这是两回事。

## UMOUNT / enforce 实测（2026-11-10 晚）

- SukiSU Ultra 的“超级用户 → App Profile”切到“自定义”后出现“卸载模块”开关（默认开），并会向 `/data/adb/ksu/.allowlist` 写入该应用的 `app_info` 记录（迅雷 uid 10345；文件 3928 → 4712 字节，正好增加一条 784 字节记录）。
- UMOUNT 生效后，迅雷进程 `/proc/<pid>/maps` 里已看不到 `zygisk_lsposed/arm64-v8a.so`、`libzn_loader.so`，也没有任何 `/data/adb` 路径；但迅雷仍在启动约 1.5 s 时被 SIGKILL（reason=2 / status=9）。
- Zygisk Next `enforce-denylist enabled`（`denylist_enforce=1`）单次实测同样被杀；`zygiskd disable-zygisk true` + 重启 zygote（注入关闭）后迅雷稳定存活（亮屏、息屏各验证一次）。
- 注意：`zygiskd disable-zygisk false` 会把 `denylist_enforce` 重置回 2（just_umount），设置 enforce 模式后不要再走 disable/enable。
- 结论：UMOUNT 只把模块**文件**从应用命名空间隐藏，Zygisk 的注入本身仍在（很可能经 zygote 继承），迅雷检测的是 Zygisk 注入层，而不是 maps 里的模块路径。按应用 UMOUNT 不能解决，必须让这些应用的进程完全不经过 Zygisk（Zygisk Next 完整 denylist 真正生效，或全局关闭 Zygisk，或让 LSPosed/Sense 可选安装）。
- 测试顺序建议：先设置 enforce 模式，再冷启动迅雷；每次改 Zygisk 配置后都需要重启 zygote 或重启设备才生效。
- `.allowlist` 记录格式与 KernelSU UAPI `uapi/app_profile.h` 对齐：`version u32 + key[256] + curr_uid s32 + allow_su bool + union`（784 字节/条，文件头 8 字节）。非 root profile 的 `umount_modules` 位于记录内偏移 273（偏移 272 是 `use_default`）。迅雷记录为 `use_default=0, umount_modules=1`，证明确实处于 UMOUNT 状态。
- 2026-11-10 22:37 复测 `enforce_denylist=1`（ENFORCED）+ 重启 zygote：迅雷仍在约 1.5 s 被 SIGKILL，maps 里无 `zygisk_lsposed`、`libzn_loader`、`/data/adb` 路径。即 Zygisk Next 1.5.3 的完整 denylist 模式对该检测仍无效，检测信号不在 maps 路径里，可能来自 zygote 继承的匿名代码/内存特征。

## 与版本差异的对应关系

- 1.5.7 一代刷机包没有内置 ZygiskNext/LSPosed，所以这些应用正常。
- 1.7.0（commit `6af5f3d` “feat(module): 1.7.0 安装时自动部署 ZygiskNext / LSPosed / Sense”）开始在安装时自动部署 ZygiskNext + LSPosed + Sense，LSPosed 从此存在于所有应用进程，用户升级后迅雷/银行开始闪退。
- Sense 依赖 LSPosed，不能简单关掉 Zygisk。

## 早期修复方向（已过时，见上文“根因 / 修复方向”）

1. **按应用彻底隐藏 Zygisk**：仅仅打开 SukiSU 的 UMOUNT（App Profile“卸载模块”）不够，实测仍被杀。需要确认 Zygisk Next 的 denylist 是否就是 SukiSU 的 UMOUNT 列表、以及哪种模式能让这些应用的进程完全不被 Zygisk 注入（`enforce_denylist` 0=disabled / 1=enabled / 2=just_umount）。如果 Zygisk Next 的注入在 zygote 层无法按进程完全隐藏，则该方法不可行。
2. **让 LSPosed/Sense 变成可选安装**：安装器里提供开关，不需要 Sense 的用户不装 Zygisk/LSPosed，从根上避免。
3. 修复后需回归：迅雷、中国银行冷启动；Sense camera 缩略图、钱包、触感等 hooks 不受影响。

## 已排除

- 模块本身（`rmx5010_fod_bridge`）的 mount/overlay：Zygisk 关闭时模块其余功能仍在，迅雷正常。
- hma_oss_zygisk、oh_my_keymint：实验时同时禁用后迅雷存活，但单独禁用 lsposed 即可存活，触发点主要是 lsposed。
