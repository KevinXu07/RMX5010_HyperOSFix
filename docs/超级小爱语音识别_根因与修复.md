# 超级小爱输入法语音识别：根因与修复

日期：2026-10-26　机型：RMX5010（GT7 Pro）　底座：原厂 16.0.7.201 + haotian OS4.0.0.19.XOBCNXM

## 1. 症状

超级小爱输入法（`com.xiaomi.type` / `MiInputMethodService`）长按麦克风后语音识别失败，
输入法弹出网络错误，日志（主路径是 Aliyun，Volc 只是回退）：

```text
ime_SpeechAsrManager: startRecording: provider=aliyun
OsbotAsrClientImpl: createEngine: provider=ALIYUN
FunAsrEngine: model=fun-asr-realtime
AudioTokenProvider: [ALIYUN] Token *** error: code=40002, msg=Device deny
ime_MiclawErrorHelper: showing toast: NETWORK: Failed to get token for aliyun
```

输入法侧选择逻辑（`MiType` 的 `AsrEngineSelector`）：

```text
aliyun not in service capabilities, fallback to volc
```

即优先 Aliyun；服务能力列表里没有 aliyun 时才回退 Volc。当前设备服务声明支持
aliyun，所以实际走 `FunAsrEngine`（`fun-asr-realtime`），用户看到的报错也是 aliyun。

## 2. 根因链

### 2.1 账号缺少 `acc_udevid` → uDevId / MiTalk 初始化失败

Xiaomi 账号（`/data/system_ce/0/accounts_ce.db` 的 `extras`）里没有 `acc_udevid`：

```text
DeviceIdGenerator: uDevId unavailable (account not logged in or no provider), returning empty
MiTalkBootstrap: DeviceIdGenerator.awaitDeviceId: uDevId unavailable after 30000ms
```

`acc_udevid` 由 `com.xiaomi.account` 的 `UDevIdService` 生成/保存，算法：

```text
acc_udevid = "ud:" + base64url(sha1(accountName + fid))[:16]
```

Realme 底包上该值缺失时，小爱/MiTalk 拿不到设备身份，后续请求全部不可用。

### 2.2 FindDevice 的 TZ 凭证不可用 → ASR 请求没有设备签名

VoiceAssist 通过 `com.xiaomi.finddevice/.v2.service.SecurityDeviceCredentialService`
获取设备签名（`X-Device-Fid` / `X-Device-Signature` / `X-Device-Ts`）。该服务直接使用
`DeviceCredentialTZ`，而 RMX5010 没有可用的小米 TZ/cardapp 凭证：

```text
DeviceSignInterceptor: [SKIP] deviceId=null, type=SDC
DeviceSignInterceptor: [REQ] fid=false, sig=false, ts=false, signType=null
```

ASR token 接口（Aliyun 主路径 `AudioTokenProvider [ALIYUN]`；Volc 回退路径
`[VOLC]`）都要求这些签名头，缺失时返回 `62001`。

## 3. 修复

### 3.1 LSPosed：FindDevice TZ → NoTZ 委托

`lsposed-src` 新增 `FdNoTzHooks`，作用域 `com.xiaomi.finddevice`：

- hook `com.xiaomi.finddevice.v2.DeviceCredentialTZ` 的
  `getFId` / `getHost` / `getOwnUserId` / `isProvisioned` / `sign` / `provision`
- 全部委托给 `DeviceCredentialManagerNoTZ`（读取 `/mnt/vendor/persist/fdsd/dc` 的软件凭证）
- `dx.i.e()` 的 TZ 判断保持不动，`SecurityDeviceCredentialService.w6()` 仍然返回 true

LSPosed 配置库新增 scope：`com.xiaomi.finddevice`（保留 `system`、`systemui`）。

### 3.2 KSU：通用 `acc_udevid` 写入

`tools/udev/UdevGeneric.java`：

1. 从 `accounts_ce.db` 读当前 `type=com.xiaomi` 的账号名
2. 从 `/mnt/vendor/persist/fdsd/dc` 的 JSON 读 `fid`
3. 现算 `ud:` + base64url(sha1(name+fid))[:16]
4. 仅在 `extras` 缺失时写入（不覆盖官方值）

`kernel-src/ksu-module/service.sh` 增加后台循环：用户解锁、CE 库出现后每 60 秒检查一次，
缺失则写入。账号/凭证变化后自动适配，不再写死任何账号的 udevid。

## 4. 验证

修复后：

```text
DeviceSignInterceptor: [OK] type=sdc, fid=true, sig=true, debugRom=false
DeviceSignInterceptor: [REQ] fid=true, sig=true, ts=true, signType=sdc
SecurityDeviceCredentialService: sign START / sign END
```

token 错误从 `62001` 变成 `40002`。主路径 Aliyun 的实测日志：

```text
ime_SpeechAsrManager: startRecording: provider=aliyun
OsbotAsrClientImpl: createEngine: provider=ALIYUN
FunAsrEngine: model=fun-asr-realtime
DeviceSignInterceptor: [REQ] fid=true, sig=true, ts=true, signType=sdc
AudioTokenProvider: [ALIYUN] Token *** error: code=40002, msg=Device deny
```

Volc 回退路径同样：

```text
AudioTokenProvider: [VOLC] Token *** error: code=40002, msg=Device deny
```

完整响应体（LSPosed hook 抓取）：

```json
{"code":40002,"message":"Device deny"}
```

同时 MiTalk 侧：

```text
ImApi: createRobot: response status=403 robotId=null, miTalkUid=null
```

## 5. 结论与残余

本地鉴权链路已经完整：

- 账号 uDevId 可读（`DeviceIdGenerator: deviceId ready`）
- MiTalk 能初始化（`rsp code=0`，link status=3）
- FindDevice 能签名（`fid/signature/ts=true`）

但小米云端仍以 `40002 Device deny` 拒绝这台设备的 ASR token 请求（Aliyun 主路径与
Volc 回退路径都一样）。把 `X-Device-Sign-Type` 从 `sdc` 强制改成 `i2c_se` 后结果不变；
MiTalk 的 `createRobot` 也返回 403。因此判定为**服务端对设备/账号的授权策略**（设备认证、
超级小爱 ASR 资格或设备登记），不是本地缺少凭证。

可继续排查的方向：

1. 用同一账号在小米真机上确认 ASR 是否可用，区分“账号无资格”与“设备被拒”；
2. 检查小米账号的设备列表 / 超级小爱资格，确认这台设备是否已登记；
3. 若服务端要求硬件级设备认证（TZ/I2C SE），Realme 硬件无法本地伪造，属于不可修范围。
