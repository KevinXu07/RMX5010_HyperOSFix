# 分区血缘与刷机顺序

## 1. 血缘表（谁来自谁）

| 内容 | 来源 | 说明 |
|---|---|---|
| system / system_ext / product | 小米 donor（当前主线：nezha OS4.0.2.0.XPACNXM，Android 17 / SDK 37） | 含 mi_ext 与 `product/pangu/system` 合并进 system-as-root |
| boot / vendor_boot / init_boot / dtbo / recovery / modem / xbl / aop / hyp / tz / abl / keymaster 等固件 | **RMX5010 原厂** | 永不使用 donor 固件 |
| vendor / odm / *_dlkm | **RMX5010 原厂**（16.0.7.201）+ 已验证增量（本仓库的账号闭包；历史上的相机 ODM、NFC 属性） | vendor/odm 只在有明确闭包时重建 |
| my_* | OS3 成品里的**精简版**（各 ~15MB） | 原厂 my_stock 4.5G + my_product 1.8G 会撑爆 super，刷大 product 前必须先刷精简版 |
| vbmeta ×3 | 原厂，但 **flags 必须打 3** | 见下 |

## 2. vbmeta flags（换底包必做）

原厂 `vbmeta` / `vbmeta_system` / `vbmeta_vendor` 的 flags = 0（开启验证）。我们是重建镜像，没有 AVB 页脚，第一阶段 init 挂载会验签失败 → **亮 logo 后黑屏重启（连开机动画都看不到）**。

修法：头部 offset 120（大端 u32）写 `0x00000003`（disable-verification + hashtree-disabled）。已刷过一次的机器可以只补刷这三张：

```bat
fastboot flash vbmeta images\vbmeta.img
fastboot flash vbmeta_system images\vbmeta_system.img
fastboot flash vbmeta_vendor images\vbmeta_vendor.img
fastboot reboot
```

### 2.1 fastboot 的坑（2026-11 整包 bootloop 根因）

`fastboot --disable-verification --disable-verity flash <分区>` **只会**给分区名以 `vbmeta` 结尾的目标写 flags
（fastboot 源码 `is_vbmeta_partition()` 用 `EndsWith(partition, "vbmeta")` 判定）。
`vbmeta_system` / `vbmeta_vendor` 不匹配，后缀参数对它们**完全无效**，实际是原样刷入 flags=0 的原厂图。

first-stage fstab 用 `avb=vbmeta_system` / `avb=vbmeta_vendor` 读取链式 vbmeta 的 hashtree；
flags=0 时照样建 dm-verity，而重建镜像没有对应 hashtree → 亮 logo 后黑屏重启。

正确做法：三张图**预先**在 offset 120 写 `0x00000003`，再普通刷入。本包 `images/` 已预置，
`verify_package.ps1` 会在刷前断言 flags==3。详见 `docs/整包刷机bootloop根因_vbmeta链式flags.md`。

## 3. 刷写顺序（整包）

```
普通 fastboot (bootloader)
  → 预检：product / current-slot / unlocked + 8 个启动分区存在性
  → vbmeta / boot / vendor_boot / init_boot / dtbo / recovery
  → fastboot -w                       # 首刷必需（清 userdata+cache）；日常单分区测试不要 -w
                                       # 失败时回退 erase userdata + erase metadata
  → fastboot reboot fastboot
fastbootd（等重枚举 + is-userspace:yes + 再等 5 秒）
  → 预检：15 个动态分区按槽位解析真实名字 + 镜像/分区尺寸 + 清理 COW 快照
  → my_engineering my_carrier my_region my_manifest my_bigball my_heytap my_product my_stock
  → vendor odm system_dlkm vendor_dlkm system system_ext product      # 均 -S 128M，保持原顺序
  → erase frp → 覆盖 vbmeta 三件套
```

铁律：

- **my_* 必须先刷**，否则大 product 会 `Not enough space to resize partition`。
- bootloader 阶段绝不刷动态分区；fastbootd 阶段绝不动 xbl/aop/hyp/tz/abl/keymaster/modem。
- 单分区验证：`adb reboot fastboot` → fastbootd → 只刷目标分区（如 `fastboot -S 128M flash vendor_a vendor.img`）→ `reboot`，**不需要 -w**。
- 主机侧 `fastboot -w` 需要 `mke2fs.exe` / `make_f2fs.exe`（在随包 platform-tools 里），否则报 `Cannot generate image for userdata`。
- 刷前会清 `cow*` 逻辑分区（虚拟 A/B 快照占 super 空间）；若设备刚推了
  OTA 还没重启，别刷。
- 普通刷写报分区缺失 / `Not enough space to resize partition` / `data too large`
  时用强力模式 `flash_os4_rmx5010_haotian_54part.bat force`，只重建有问题的逻辑
  分区。流程参考见 `docs/欧加线刷流程参考_VioletToolBox.md`。

## 4. 刷前核对

```
[ ] 序列号正确（-s <serial>）；本机另一台设备绝不操作
[ ] 镜像 SHA-256 与 metadata 清单一致；product 尺寸约 4.35G（截断镜像禁刷）
[ ] fsck.erofs（raw）通过；sparse 回读一致
[ ] 本轮只改计划内的分区
[ ] 磁盘余量足够（单 product raw+sparse 约需 8.7G）
```

## 5. 刷后回读基线

```
sys.boot_completed=1
getenforce=Enforcing
关键文件 sha256 回读（账号闭包：odm/vendor 的 selinux 上下文文件、/odm/bin/mtd）
logcat / dmesg 无对应进程 FATAL、无 "Context ... is not valid"
```
