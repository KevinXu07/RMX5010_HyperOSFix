# 超级小爱 ASR 鉴权逆向：读取清单与代码路径

日期：2026-10-26　机型：RMX5010（GT7 Pro）　底座：原厂 16.0.7.201 + haotian OS4.0.0.19.XOBCNXM

> 结论先行：超级小爱 ASR 的**请求级鉴权**只读两类东西——Xiaomi Passport 的 `miclaw`
> service token（Cookie）和 FindDevice 的设备签名头（X-Device-*）。序列号只在
> **Passport 登录/设备注册环境**里被读取，不在 ASR 请求头里；vendor/Oplus 指纹、
> 相机、屏幕密度、bootloader 状态**都不参与 ASR 鉴权**。

## 1. 请求级鉴权（Aliyun 主路径）

请求：

```text
GET {AudioTokenApiUrl}?model=aliyun
```

### 1.1 账号 service token（Cookie）

代码：`ServiceTokenHttpClient`（混淆名 `er/a0$b`），由
`buildServiceTokenCookie$network_release` / `replaceServiceTokenCookie$network_release`
注入。Cookie 字段：

```text
cUserId=<ServiceTokenResult.k>
userId=<ServiceTokenResult.n>
serviceToken=<ServiceTokenResult.b>
miclaw_serviceToken=<ServiceTokenResult.b>
miclaw_ph=<ServiceTokenResult.j>
miclaw_slh=<ServiceTokenResult.i>
```

serviceId 来自 `com.aios.osbot.data.repository.f1`：

```text
MICLAW_API        = "miclaw"          ← ASR / audio proxy 使用
MICLAW_ECOLOGY    = "miclaw-ecology"
MICLOUD           = "micloud"
STORE             = "hyperos_miclaw_api"
MIUI_VIP / XIAOMIIO / MIJIA / OAUTH2
```

token 获取链：

```text
AccountRepository.getServiceToken(f1.MICLAW_API)
  -> ik/f.isAccepted()                     # CTA 未接受直接返回 null
  -> n0.getServiceToken("miclaw")
  -> com.xiaomi.passport.accountmanager.i.getServiceToken(account, "miclaw", Bundle)
  -> ServiceTokenResult { serviceToken, cUserId, userId, ph, slh }
```

实测：CTA 已接受，service token 有效；聊天/LLM 请求也使用同一套 token 并返回 200。

### 1.2 设备签名头

代码：`DeviceSignInterceptor`（混淆名 `gr/c`）。只加六个头：

```text
X-Device-Fid
X-Device-Signature
X-Device-Ts
X-Device-Sign-Type     # sdc / i2c_se / none
X-Device-Type          # phone / pad / speaker / tv
X-Device-Debug-Rom     # true / false
```

各值来源（代码级）：

| 头 | 读取 | 我们的值 |
|---|---|---|
| `X-Device-Type` | `hr/b.getCurrent()` 读 `ro.build.characteristics`：含 tablet/speaker/tv 才切换，否则 PHONE | `nosdcard` → `phone` |
| `X-Device-Sign-Type` | `hr/l.getProviderType()` → `hr/m`（SDC / I2C_SE / NONE） | `sdc` |
| `X-Device-Debug-Rom` | `tu/q.isDebugRom()`：`(Build.TYPE != "user") \|\| ro.debuggable` | `user` + `0` → `false` |
| `X-Device-Fid/Signature/Ts` | FindDevice `SecurityDeviceCredentialService` → `DeviceCredentialTZ`（本项目已委托 NoTZ） | `fid=true, sig=true, ts=true` |

注意：`Build.FINGERPRINT` 只作为 `debug-rom-<hashCode>` 的**本地缓存 key**，
不直接发送；`X-Device-Debug-Rom` 是上述布尔值。

### 1.3 User-Agent

`bk/q.buildUserAgent()`（`bk/q.v()`）读取：

```text
ro.product.model              = 2410DPN6CC
ro.product.marketname         = Xiaomi 15 Pro
ro.miui.ui.version.name       = V816
ro.mi.os.version.name         = OS4.0
ro.mi.os.version.incremental  = OS4.0.0.19.XOBCNXM
ro.miui.region                = CN
ro.product.mod_device         = haotian
```

全部为 Xiaomi/haotian，不含 vendor/Oplus/序列号。

## 2. Passport 登录/设备注册环境（序列号在这里）

代码：MiType 的 `com.xiaomi.passport.PassportUserEnvironment`，调用方：

- `com.xiaomi.passport.uicontroller.PhoneLoginController$6`
- `com.xiaomi.passport.utils.AccountHelper`
- `com.xiaomi.passport.ui.utils.AccountLoginer$4`

`getEnvInfoArray()` 读取并 base64/hash：

```text
Build.MODEL                       # 2410DPN6CC
Build.SERIAL                      # Realme 序列号（本项目为 acbefdc7）
Settings.Secure.ANDROID_ID
网络类型
```

该环境在**账号登录/设备注册**时上报。实测小米账号“登录设备管理”里：

- 当前设备名：`Leitzphone powered by Xiaomi`（不是 Realme/RMX）
- 2026-10-18 有 **3 条重复的 Leitzphone 记录**
- 另有用户真实的小米 15 Pro 记录

所以序列号可能进入 Passport 设备环境/风险评分，但**不在 ASR 请求头里**。

## 3. MiTalk / uDevId

`DeviceIdGenerator`（`tu/u`）：

```text
getDeviceDisplayName()  -> Build.BRAND / Build.MODEL / ro.build.characteristics
readUDevId()            -> 账号 userData 的 acc_udevid
```

`acc_udevid` 的生成/写入见 `docs/超级小爱语音识别_根因与修复.md` 与
`tools/udev/UdevGeneric.java`。MiTalk/robot 使用 uDevId；ASR token 请求本身不直接带 uDevId。

## 4. 输入法的 provider 选择

MiType `AsrEngineSelector`（`s8/f`）：

```text
requestedProvider = aliyun（默认/配置）
supported_asr_engines 来自服务能力
if (aliyun in supported) use aliyun
else log "aliyun not in service capabilities, fallback to volc" -> volc
```

当前设备服务声明支持 aliyun，所以实际走：

```text
SpeechAsrManager: provider=aliyun
OsbotAsrClientImpl: createEngine: provider=ALIYUN
FunAsrEngine: model=fun-asr-realtime
```

Volc 路径（`VolcAsrEngine`）只是回退。

## 5. 明确**不参与** ASR 鉴权的 prop

以下 prop 虽然和真机不一致，但不在 ASR 请求头/UA/签名头中：

```text
ro.product.vendor.* / vendor_dlkm / bootimage（oplus/ossi）
ro.vendor.build.fingerprint / vendor_dlkm / bootimage（oplus/ossi:15）
ro.vendor.build.version.sdk/release（35/15）
ro.vendor.oplus.* / ro.vendor.config.oplus.*
ro.vendor.oplus.market.name（RMX5010）
persist.sys.device_name（Realme GT7 Pro）
ro.vendor.oplus.camera.*
ro.sf.lcd_density（500）
ro.boot.verifiedbootstate / flash.locked / secureboot.lockstate
ro.serialno / ro.boot.serialno（序列号只在 Passport 登录环境读取）
```

因此“把 vendor/Oplus prop 全改成 Xiaomi”不会改变 ASR 的请求级鉴权输入；它只影响
账号/设备注册环境和设备完整性判断。

## 6. 40002 Device deny 的剩余假设

本地已提供：

```text
账号 service token（miclaw）     ✅
设备 fid/sig/ts                  ✅
X-Device-Type=phone              ✅
X-Device-Debug-Rom=false         ✅
User-Agent 全 Xiaomi             ✅
```

服务端仍返回：

```json
{"code":40002,"message":"Device deny"}
```

Aliyun 与 Volc 两条 token 路径结果相同；把 `X-Device-Sign-Type` 强制改成 `i2c_se`
也不变。结合以下现象，判定为**服务端设备授权/风控**，不是本地缺字段：

1. 账号设备列表有 3 条重复 Leitzphone（设备数 26），可能触发重复设备/设备数风控；
2. FindDevice 使用的是**软件 SDC 凭证**，ASR 可能要求硬件 TZ/SE 认证；
3. 同一账号 `Chat:false`、MiTalk `createRobot` 403，可能是超级小爱 ASR 资格未开通；
4. Passport 登录环境里的 Realme 序列号可能影响设备风险评分（不在 ASR 请求头里）。

建议的下一步：在小米账号“登录设备管理”里删除多余的 Leitzphone 记录（保留当前设备），
再试一次语音；若仍 40002，基本只剩 SDC 硬件认证/ASR 资格，属于服务端策略。
