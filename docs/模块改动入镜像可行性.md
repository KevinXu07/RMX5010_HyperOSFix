# 模块 / Sense 改动能否落进镜像（2026-11-17 离线分析）

问题：模块和 Sense 在运行时做的改动，哪些能直接做进分区镜像？之前改过 APK
（Settings、两个 Devices overlay）做进镜像，`-w` 后 PMS 不认。

结论先行：**PMS 并不校验预置 APK 的内容摘要**，之前失败的真正原因是
`resources.arsc` 重打包后没有 4 字节对齐（以及一个 overlay 的签名块被剥掉）。
按规则重打包的 APK 可以进镜像；但 Sense 的 hook 要改写成每个 ROM 版本单独做的
dex 补丁，工作量和维护成本都在这里。

## 1. PMS 对预置 APK 的实际检查（4.0.4.0 services.jar / framework.jar 反编译）

| 检查 | 对系统分区 APK 是否生效 | 依据 |
|---|---|---|
| 签名内容摘要（v2/v3 digest） | **不校验** | `InstallPackageHelper.scanSystemPackageLI`：`scanSystemPartition = (parseFlags & 0x10 /*PARSE_IS_SYSTEM_DIR*/) != 0`，原样作为 `skipVerify` 传给 `ScanPackageUtils.collectCertificatesLI` → `ParsingPackageUtils.getSigningDetails(..., skipVerify)`，只从签名块里取证书 |
| 签名块里必须有 v2 及以上签名 | 生效，但**只在首次登记时** | `getSigningDetails` 按 targetSdk 定最低方案：≥30 为 v2（`ApkSignatureVerifier.getMinimumSignatureSchemeVersionForTargetSdk`），只有 v1 时报 “No APK Signature Scheme v2 signature in package”。但 `ScanPackageUtils.collectCertificatesLI` 有优化：packages.xml 已有该包、路径相同、mtime 相同时直接沿用记录里的证书，根本不读 APK。模块把文件 mtime 设成 0（和原厂一样），所以剥了签名块的 overlay 在不清数据时也能用，`-w` 后才会被拒 |
| `resources.arsc` 不压缩且 4 字节对齐 | **生效，没有系统分区豁免** | `ParsingPackageUtils.parseBaseApk`：`AssetManager.containsAllocatedTable()` 为真时 `deferError("Targeting R+ … stored uncompressed and aligned on a 4-byte boundary", 132742131)`，targetSdk ≥ 30 即报错 -124，包被跳过 |
| 已有数据时 | 不重新解析 | PMS 用 `/data/system/package_cache` 和 packages.xml 里的旧结果（路径 + mtime 不变就沿用），所以改坏的 APK 在不清数据时“看起来能用”，`-w` 后首扫才暴露 |

### 2.1 实机复验（2026-11-17，OS4.0.0.19 机器）

不刷分区：模块本来就在 post-fs-data 把 `overlay/` 下两个 APK bind 到
`/product/overlay`，只换模块目录里的文件，每轮删 `/data/system/package_cache`
后重启，让 PMS 重新解析。原文件备份在手机 `/data/local/tmp/ovl_backup_20261117/`。

| 轮次 | DevicesOverlay（目标 SystemUI） | DevicesAndroidOverlay（目标 android） | 结果 |
|---|---|---|---|
| A | 模块原版：arsc **未对齐**，签名块拼回 | 模块原版：arsc 对齐，**无签名块** | DevicesOverlay 被丢弃（uiderrors：`System package com.miui.systemui.devices.overlay no longer exists`）；DevicesAndroidOverlay 仍被识别——packages.xml 有记录且 mtime 相同，证书直接沿用，没读 APK |
| B | 对齐版（`zipalign -p 4` 后拼原厂签名块），条目内容与模块原版逐个相同 | 故意做的 **未对齐** 版（拼原厂签名块） | **system_server 开机循环崩溃**：`Unable to parse: /data/apex/decompressed/com.android.*.decompressed.apex`，Caused by “Targeting R+ … resources.arsc … aligned on a 4-byte boundary”。崩在 APEX 扫描阶段，没有像 A 那样只跳过一个包；具体的错误串扰路径没追 |
| 恢复 | 对齐版 | 对齐版（拼原厂签名块） | 正常开机，两个都在 `pm list packages` 里且 `cmd overlay list` 为 `[x]`；DevicesOverlay 的 packages.xml 记录已在 A 被清掉，这次是真正的首次登记，证书从拼回的签名块读出，内容摘要不符也没关系 |

结论：

1. **arsc 对齐是硬条件，已实机确认**。未对齐的 overlay：目标是 SystemUI 的被跳过，目标是 `android` 的直接让 system_server 起不来。所以以后做进镜像的 APK 必须先过 `zipalign -c -p 4`。
2. **拼回原签名块、内容摘要不符的 APK 可以首次登记**，已实机确认（DevicesOverlay 对齐版）。
2b. **`-w` 实测**（2026-11-17 刷入合入版整包）：两个对齐 + 拼回原厂签名块的 overlay 在清数据后的首次开机被正常登记、`cmd overlay list` 为 `[x]`。
3. **剥掉签名块会在 `-w` 后被拒**：只有代码依据，没有实机复现。要让 DevicesAndroidOverlay 走首次登记，得先清掉它在 packages.xml 里的记录；手头唯一的办法是放一个解析失败的版本，而 B 轮表明这样会卡开机，所以没做。
4. 模块现在的 overlay 能用，靠的是两层缓存：解析结果靠 package_cache，证书靠 packages.xml，两边都是 mtime=0 命中。清缓存或 `-w` 后就会失效。手机上的模块目录已换成两个对齐版（与模块原版条目内容相同），仓库里的 `kernel-src/ksu-module/overlay/` 还是旧文件。

### 2.2 签名块里带“内容长度”的 APK（2026-11-18，钱包套件实测）

第 1 节“只取证书、不校验内容”还有一个例外：**APK 文件变了（路径相同、mtime 不同）
时 PMS 会重新收集证书**（`ScanPackageUtils.collectCertificatesLI`，日志
`/product/app/X changed; collecting certs`），即使 `skipVerify=true`，
`ApkSignatureVerifier` 解析 v2/v3 块时仍会核对 **`VERITY_CHUNKED_SHA256`（算法
`0x0421`）摘要里记录的内容长度**（APK 总长减去签名块长度）。长度不符就报：

```
W PackageManager: Failed to scan /product/app/CosWalletTasWallet:
  Failed to collect certificates from .../TasWallet.apk using APK Signature Scheme v3
```

包被当成“已不存在”，**数据随之被清掉**（`pm_critical_info: System package ...
no longer exists; its data will be wiped`）。Settings 能过，是因为它的 v2/v3 只有
`0x0103`（CHUNKED_SHA256），不记长度。

| APK | v2/v3 摘要 | 改后能否直接拼块 |
|---|---|---|
| Settings、SecureElement、XMNfcNci、MITSMClient、EidService | 只有 `0x0103` | 能（长度随便变） |
| FinShellWallet、TasWallet、UPTsmService | `0x0103` + `0x0421`（记录长度） | 不能，必须补齐到原长度 |

查法：`python3 vs.py x.apk` 的同类脚本，或看 `scripts/apk_repack.py` 输出的
`verity source length`。

**补齐办法**（`scripts/apk_repack.py <原 APK> <补丁 zip> <输出>`）：
1. 未改动的条目按原压缩字节原样搬运（CRC、大小都不变）；
2. 改过的条目用 zlib 9 与 7-Zip deflate 中较小者压缩；
3. 不压缩条目按 zipalign -p 规则对齐（`.so` 4096，其余 4）；
4. 用中央目录 extra 字段（id `0x5250`，单条最多 65535 字节）加 EOCD 注释把内容补到原长度；
5. 拼回原签名块，自检内容长度等于 verity 记录。

改后内容必须**不大于**原版才能补齐。smali 重新汇编的 dex 比原版大（原版由 R8/d8
产出，共享代码块、调试信息更紧凑），钱包这类 dex 带完整调试信息的，
`baksmali d --debug-info false` 去掉 `.line/.local` 后 dex 就明显变小（FinShell 9 个
dex 共小 1.7 MB，TAS 小 0.9 MB）；调试信息本来就少的（UPTsmService），靠 7-Zip
deflate 比 zlib 9 小约 3.5% 腾出空间。不要删 `META-INF` 里的 v1 文件腾空间：
FinShell 内置的腾讯 turingcam（人脸/风控）会用 `JarFile` 读 APK 的 v1 证书。

另：**原 APK 里 dex 是不压缩存放的**（MITSMClient），smali 重新汇编后约大 40%；
这种不带长度摘要的可以把改过的 dex 改成 deflate 存放（系统应用照常由 ART 解出编译），
APK 反而变小（32.8 → 27.5 MB）。

## 3. 改 APK 进镜像的规则

1. 只改 dex / 资源，保留原 APK 的 v1 `META-INF` 和 v2/v3 签名块（内容摘要失效没关系）。
   签名块带 `0x0421`（verity，记录内容长度）的，必须用 `scripts/apk_repack.py`
   补齐到原长度（2.2），否则开机收集证书失败、包和数据一起没了。
   现在所有新改的 APK 都统一走 `apk_repack.py`（它也负责对齐和拼块）。
2. 重打包后先 `zipalign -p -f 4`（`resources.arsc` 4 字节、未压缩 `.so` 按页对齐），
   **再**把原签名块拼回中央目录前（拼块只移动中央目录，不影响条目对齐）。
   出镜像前用 `zipalign -c -p 4` 检查；目标是 `android` 的 overlay 不对齐会让
   system_server 开机循环（2.1 B 轮）。
3. 删掉该 APK 的 `oat/`（odex/vdex 校验和对不上会被 ART 丢弃，留着只是浪费）以及对应的 `.fsv_meta`。
4. framework 下的 jar（services.jar、miui-services.jar）没有签名要求，改 dex 后删
   `oat/arm64/<jar>.{odex,vdex,art}`，miui-services 指纹桩就是这样做的。
   **不要改 boot classpath 的 framework.jar**：boot image 失效会让 zygote 每次开机重编。
5. APEX 里的 APK（如蓝牙 `com.android.bt.apex`）不能改：apexd 校验 APEX 签名和 hashtree。

### 4.3 不能或不适合进镜像

| 改动 | 原因 |
|---|---|
| BluetoothHooks（LHDC） | 目标在 `com.android.bt.apex` 里，APEX 不能改 |
| 钱包 5 件套及其进程内 hook | 第三方应用装在 /data，会被商店更新覆盖 |
| 触控报点率、触感强度、游戏帧率、FOD 触摸桥的运行时写入 | 跟随 Sense 设置实时变化，需要 root 常驻脚本；做成 init 服务要为每个脚本单独写 SELinux 域。双击亮屏后来找到不用新域的办法，见 4.6 |
| 推送 / Greeze 的运行时设置、钱包锁屏 AppOp、acc_udevid、LSPosed 作用域注册 | 写 /data 或系统设置，不属于分区内容 |
| ZygiskNext / LSPosed / Sense 本身 | 框架层，只要还有 hook 就要保留 |

SELinux 三条规则先离线验证过：用手机自己的 `/system/bin/secilc`，按 init 的参数（`-N`）把 4.0.4.0 的 plat/system_ext/product 和 vendor 策略一起编译，改前改后都成功；严格模式下改前改后同样是 23 处 neverallow（都是原厂 vendor 自带的），没有新增。odm 里的 `precompiled_sepolicy` 本来就和 4.0.4.0 对不上，开机一定现编。

构建后逐文件核对（`meta.py` 式比对：类型、权限、属主、SELinux 标签、capability、内容）：

- odm（对回读原厂）：2740→2741 项，只有 1 个新增库和 6 个预期的内容变化，没有删除，元数据零变化。
- vendor（对回读原厂）：3903→3913 项，新增 rc、目录和 8 个 .ko，`build.prop` 与 3 个 seccomp 策略内容变化。第一次构建时 `build.prop` 的标签丢了（`sed -i` 换了 inode），脚本已改成原地改写。
- system / system_ext / product（对未合入的 4.0.4.0 镜像）：分别新增 26 / 108 / 73 项、内容变化 2 / 4 / 7 项，没有删除，原有路径的标签和权限全部不变。
- odm / vendor 按规范用 `-zlz4 -C262144`，superblock 特征与原厂一致（lz4、big_pcluster）。
- 几个 APK（两个 overlay、OplusCamera、两个桩）都有 v2/v3 签名块，`resources.arsc` 对齐。

2026-11-17 实机（`-w` 刷入、未装模块时）：props 全部生效；`/proc/modules` 有 7 个 millet 和 `rmx5010_fod_bridge`；两个 overlay、相机、两个桩、IFAA 都在 `pm list packages` 里；`/mi_ext` 软链可读；QESDK 三个服务和 millet_monitor 开机后不再重启；首次开机日志无解析失败，也没有与相机、IFAA、加载内核模块有关的 SELinux 拒绝。日志里有一个 init 子进程在开机 19 秒时 SIGABRT（无其它记录，需 root 查 dmesg）。
